# 家計簿アプリ 設計メモ

利用者: 1名 / ランニングコスト: ¥0 / iPhoneから利用（PWA）

## 技術スタック

| 用途 | 採用 | 無料枠 |
|---|---|---|
| フロント/API | Next.js on Vercel Hobby | 個人・非商用は無制限、`*.vercel.app` 利用で独自ドメイン不要 |
| DB / 認証 | Supabase Free | DB 500MB（想定 年6,000件 ≒ 数十年分） |

| iPhone配信 | PWA（ホーム画面に追加） | 無料。Apple Developer Program 不要 |

注意: Supabase Free は1週間アクセスが無いとプロジェクトが一時停止する。毎日利用するため実害は無い想定。

## 2. 重要な設計判断

### 方針1: iD は口座にしない
iD は「三井住友カード デビュープラス」の決済チャネルであり、独立した資金源ではない。
口座として作ると同じ支出が2件計上される。iD利用分は デビュープラス の取引として記録し、
決済手段は `channel` タグ（`id` / `card` / `apple_pay`）で区別する。

### 方針2: NISA積立は「支出」ではなく「振替」
楽天カードによるNISA積立を支出計上すると、支出額が実態より大きく膨らむ。
    楽天カード → 楽天証券   type = transfer  （毎月100,000円 = つみたて投資枠）
    京都銀行  → 楽天証券   type = transfer  （不定期の入金 = 成長投資枠。NISA満額用）
純資産は正しく増加し、月次支出は汚れない。
「投資額」を見たい場合は振替のうち `to_account.type = securities` のものを別集計する。

### 方針3: 現金は「引き出した時点で支出」
本人の要望により、現金の使途は追跡しない。現金口座を作ると残高が減らずに溜まり続けるため、
    ゆうちょ銀行 → 支出（費目: 現金引出）
として引き出し時に確定させる。将来使途を追いたくなったら現金口座方式へ移行する。

### 方針4: ポイントは管理対象外（Phase 4以降で再検討）
Vポイント / 楽天ポイント / ZOZOポイント / Amazonポイント / リクルートポイント。
いずれも自動取得手段が乏しく、手入力コストに対して家計把握上の価値が低い。
ポイント払いした支出は「その分だけ支出が少ない」として自然に処理される。
残高を把握したくなった場合のみ、月1回の手動スナップショットを追加する。

### 方針5: PayPay は残高口座を持つ / ICOCA は簡易処理
PayPay は残高チャージが主体のため、資産口座として残高を管理する。

    京都銀行 → PayPay残高      transfer（チャージ）
    PayPay残高 → 支出           expense（利用）
    友人 → PayPay残高           income（費目: 送金受取・立替精算）
    PayPayカード払いの利用分     expense（account = PayPayカード）※残高を経由しない

チャージを支出計上すると二重計上になる。また PayPay は「残高払い」と「PayPayカード払い」が
混在するため、取り込み時に支払方法で `account_id` を振り分ける必要がある。

ICOCA は無記名かつクレジットチャージのため、残高の正確な追跡が困難。
チャージ時点で即 `交通費` として支出計上する簡易処理を採用し、残高は管理しない。
チャージはクレジットカード明細に現れるため、その1行を交通費に分類するルールで足りる。

### 方針6: 支出の発生主義
カード利用日に支出計上し、引落日は銀行→カードの振替として扱う。
    3/15  カード利用 5,000  → expense（食費） / カード負債 +5,000
    4/27  銀行引落 5,000    → transfer（京都銀行 → カード）
カードごとに締め日・支払日を保持し、次回請求予定額を算出する。

## 3. データ取得経路

原則: **カード類はメール速報が主役、銀行はCSVが主役。**

ただし実物のメールで分かったとおり（13章）、**三井住友カードは「携帯電話や公共料金などの
継続的なご利用」と「ETC・PiTaPa等の一部の電子マネー」を通知しない。**
サブスク・電気代・ICOCAチャージはメールに現れないため、**カードについても
CSVの月次取込は必須**。速報は日々の変動費、CSVは固定費を含む確定値、と役割を分ける。

### メール自動取得（Gmail + GAS）
| 対象 | 実測 | 備考 |
|---|---|---|
| Amazonカード | ○ | 三井住友カードのご利用通知。文面はデビュープラスと同じはず（実物未確認） |
| 三井住友 デビュープラス | ○ | **確認済み**（2026-09-23）。カード名・店名・金額が取れる。ただし下記の穴あり |
| 楽天カード | ？ | 利用お知らせメールの実物が未着（積立は月1回のみのため） |
| PayPayカード | ？ | 実物が未着。アプリのプッシュのみの可能性は残る |
| ZOZOカード | ○ | **確認済み**（2026-09-23）。ただし**店名は出ない**（13章） |
| PayPay残高 | × | アプリ内通知のみの見込み。PayPayアプリの取引履歴CSVで代替（支払方法の列が要る） |
| Amazon.co.jp 注文確認メール | 補助 | 店名ではなく商品名が取れるため費目推定に有用。金額の正はカード速報側（二重計上させない） |

構成:
    Gmail → GAS（5〜10分間隔トリガー、GmailApp.search）
         → 自作API に POST（共有シークレットで認証）
         → パース → 未分類トレイ or ルール適用で自動確定

### CSVインポート
必要なパーサーは6種。三井住友は Vpass で2枚まとめて取得できるため1パーサーで済む。

1. 京都銀行（京銀ダイレクト）
2. ゆうちょ銀行（ゆうちょダイレクト）
3. 三井住友カード / Vpass … Amazonカード + デビュープラス
4. 楽天カード / 楽天e-NAVI
5. PayPayカード
6. ZOZOカード

各ファイルの実フォーマットは「9. CSV仕様」を参照（実物で確認済み）。
照会可能期間が短いため、未取込月を検出するリマインドは必須機能とする（9.4）。

### 重複排除（必須）
同一取引がメール速報とCSVの両方から入る。

    dedup_key = 日付±3日 + 金額一致 + 正規化店名の類似度
    CSV を正とし、メール由来レコードを上書きマージする

## 9. CSV仕様（実ファイルで確認済み・2026-09-22）

両行とも **文字コード CP932（Shift_JIS）**。UTF-8 として読むと確実に壊れるため、
パーサーは cp932 で明示デコードする。

### 9.1 ゆうちょ銀行（ゆうちょダイレクト）

ファイル名例: `202609223620_01.csv` / 改行: LF

**先頭6行はプリアンブル（ヘッダーではない）:**

    1: お客さま口座情報
    2: 現在高：,"227,729",円,
    3: 出力日時：令和 08 年 09 月 22 日 17 時 36 分   ← 和暦。西暦 = 令和年 + 2018
    4: お客さま口座番号：XXXXX-XXXXXXXX
    5: 照会対象：全期間
    6: 明細件数：7                                    ← 取込件数の検証に使う
    7: （ここがヘッダー行）

**ヘッダー（7行目）:**

    取引日,入出金明細ＩＤ,受入金額（円）,払出金額（円）,詳細１,詳細２,現在（貸付）高,

- 「ＩＤ」は全角。末尾にカンマがあり列数が1つ多く見える（空列として捨てる）
- `取引日`: `YYYYMMDD`（区切りなし）。年が入っているため推定不要
- `入出金明細ＩＤ`: 取引ごとにユニーク → **そのまま dedup キー／冪等キーに使える**
- `受入金額` = 入金、`払出金額` = 出金。片方が空
- `詳細１` = 取引種別（`カード` `手数料` `ことら` `給与` `料　金` `振込`）
  ※ `料　金` は全角スペースを含む → 正規化してから判定する
- `詳細２` = 相手方（半角カナ）
- 金額・残高はカンマなしの素の数値（プリアンブルのみカンマ付き）

**分類ルール（詳細１ベース）:**

| 詳細１ | 扱い |
|---|---|
| カード | ATMでの現金引き出し → 支出（費目: 現金引出）※方針3 |
| 手数料 / 料　金 | 支出（費目: 手数料）… ATM時間外手数料など |
| 給与 | 収入（給与・第二振込） |
| ことら / 振込（個人名） | 収入（送金受取・立替精算） |
| 振込（法人名） | 内容により判断 |

### 9.2 京都銀行（京銀ダイレクトバンキング）

ファイル名例: `ny20260922172847.csv` / 改行: CRLF / 全フィールドがダブルクォート囲み

**プリアンブルなし。1行目がヘッダー:**

    "番号","明細区分","取扱日付","起算日","お支払金額","お預り金額","小切手","取引区分","残高","摘要"

- **`取扱日付` に年が無い**（例: `"7月3日"`）
  → ファイル名の `ny<YYYYMMDDhhmmss>` からダウンロード日を取得し、
     「その年で組んだ日付がダウンロード日より未来なら前年」として補完する
- `番号` は日ごとに `001` から振り直される連番。**ユニークIDではない**
  → dedup キー = hash(日付, 番号, 金額, 摘要, 残高)
- 金額は `\712,869` 形式。先頭の `\`（CP932上の円記号）とカンマを除去してから数値化
- `お支払金額` = 出金、`お預り金額` = 入金。片方が空
- `明細区分` `起算日` `小切手` は常に空 → 無視
- `摘要` は半角カナで、**長い名称は途中で切れる**（`ﾊﾟﾅｿﾆﾂｸｲﾝﾀﾞｽﾄﾘ-(ｶ`）
  → マッチングは **NFKC正規化 + 前方一致**。銀行表記は小書き文字を使わないため
     （`ﾆﾂｸ` = ニック）、正規化で ッ/ャ/ュ/ョ の揺れも吸収する

| RS PAYPAY | 振替（京都銀行 → PayPay残高）＝チャージ |
| ﾐﾂｲｽﾐﾄﾓｶ-ﾄﾞ (ｶ | 振替（カード引落）※9.3の曖昧性あり |

### 9.4 照会可能期間（重要な制約）

| 口座 | 遡れる範囲 | 当月を0とした遡及月数 |
|---|---|---|
| 京都銀行 | 前々月まで（当月含め3ヶ月） | 2 |
| ゆうちょ銀行 | **先月まで（当月含め2ヶ月のみ）** | 1 |

ゆうちょは画面上「全期間」と表示されるが、**実際には先月・今月の2ヶ月分しか
ダウンロードできない**（2026-09-22 に確認）。当初「全期間で8月の7件しか出ない」と
見えていたのはこのためで、開始日を指定しても遡れない。京都銀行より条件が厳しい。

ある月 M の明細は「M の遡及月数ヶ月後の末日」を過ぎると二度と取得できない。
例: ゆうちょの8月分は9月末を過ぎたら永久に失われる。

→ **毎月1日に前月分の取り込みを促すリマインドを実装する（必須機能）。**

判定は `src/lib/import-window.ts`（テスト済み）。

### 9.5 残高チェーン検証（欠落検出の要）

京都銀行・ゆうちょとも各行に残高を持つため、次式で取引の欠落を機械的に検出できる。

    前行の残高 + 入金 - 出金 == 当行の残高

京都銀行は前々月までしか遡れないため、「取り込み漏れが無いこと」を
この検証で保証することが不可欠。実データ（2026-07-03〜2026-09-06、27件、
3ファイル）で検証したところ不整合 0 件で、フォーマット解釈の正しさも確認できた。

実装方針:
- インポート時に、既存データの最終残高と新ファイルの先頭行が繋がるか検証する
- 繋がらない場合は差額と推定欠落期間を提示し、再ダウンロードを促す
- ファイルのMD5が既知のものと一致する場合は取り込みをスキップする
  （実例: ny20260922172847.csv と ny20260922174646.csv が同一内容だった）

### 9.6 特別支出・経費精算の分離（通常の月次収支から外す）

判明した2件は、いずれも「毎月の生活費」ではないため、月次収支にそのまま混ぜると
家計の実態が読めなくなる。

**国民年金の追納（学生納付特例分）**
`PE ｼﾔｶｲﾎｹﾝﾘﾖｳﾄｳ(ｺﾂｺｷﾝ)` 2026-08-30〜08-31 に5件・合計 643,100円。
事業用ではなく本人の支出だが、過去分をまとめて納付した**一時的な特別支出**。
費目「社会保険料 > 国民年金追納」とし、特別支出として扱う。
※社会保険料控除の対象になるため、年末調整・確定申告用に年間合計を出せるようにする。

**経費精算（出張交通費の会社からの払い戻し）**
`ﾊﾟﾅｿﾆﾂｸｸﾞﾙ-ﾌﾟ ｼﾕｳﾁﾕｳﾌﾘｺﾐ` は給与ではなく、出張交通費の立替払い戻し。
通常の収入に混ぜると収入が水増しされる。費目「経費精算」とし、通常収入から除外する。
対応する立替支出は本人のカードで発生しているため、両建てで計上すれば相殺されて正しくなる。

**実装:**

    categories に is_extraordinary (boolean) を追加
      true の費目は「通常の月次収支」グラフから除外し、別枠で表示する
      対象: 国民年金追納 / 経費精算 / その他の一時的な収支

### 9.7 銀行明細に現れない固定費（カード払い）

銀行引落で確認できた固定費は水道（`ﾈﾔｶﾞﾜ ｽｲﾄﾞｳ`）のみ。残りはカード払い。

| 費目 | 支払方法 | 備考 |
|---|---|---|
| 水道 | 京都銀行 引落 | `ﾈﾔｶﾞﾜ ｽｲﾄﾞｳ` |
| 電気 | 三井住友カード | JAPAN電力 → **オクトパスエナジーに変更済み**（摘要が変わる） |
| 携帯 | PayPayカード（の見込み・要確認） | カード明細で確認する。**このカードは通信費専用ではない**ので、口座で費目を決め打ちできない |
| ガス | 不明 | カード明細で確認する |
| 家賃 | 給与天引き | 明細に現れない（9.7） |

**契約先変更で摘要が変わる問題:**
電気の供給元変更のように、同じ費目でも摘要が突然変わることがある。
ルールエンジンは既知の摘要しか分類できないため、**未知の摘要は必ず未分類トレイに送り、
そこで1回分類したらルールとして学習する**という流れを必須とする。
この「未分類トレイ → ルール学習」が、長期運用で破綻しないための中核機能になる。

### 9.8 給与天引きされているもの（明細に現れない）

家賃は会社が給与から天引きしているため、銀行明細にも家計簿にも現れない。
給与は天引き後の手取りで入金されるので、**収入・支出とも計上しないのが正しい**
（収支としては整合する）。住居費を可視化したくなった場合のみ、給与明細から
手動で両建て計上する。

マスクしたサンプルを `tests/fixtures/` に置く（`.gitignore` で例外許可済み）。

    ユニクロ・ＧＵ・ＰＬＳＴオンライン（買物）    9,980円

- **本文にカード名が入る。** これで 9.3 の「銀行明細では三井住友カード2枚を
  区別できない」問題は、メール側から解ける見込みが立った
- 店名・金額・日時（分まで）が取れる。全角とNBSPだらけだが NFKC で畳める
- 店名の末尾に利用区分（買物）が付く。CSVの摘要には付かないため**切り離して保存する**。
  付けたままだと、同じ店なのにメール由来とCSV由来でルールが別々に必要になる

**⚠️ 本文は「メールアプリの見た目」とは別物（2026-09-23 判明）**

上のHTML版の見た目に合わせてパーサーを書いたところ、1通も読めなかった。
GAS が送ってくるのは `getPlainBody()`、つまり**プレーンテキスト版**であり、
実物はこの形をしている:

    ご利用カード：三井住友カードデビュープラスＶＩＳＡ

    ◇利用日：2026/09/23 12:50
    ◇利用先：エスト／ＮＦＣ
    ◇利用取引：買物
    ◇利用金額：4,400円

項目名が付いて縦に並ぶ。HTML版のように利用先と金額が横並びになることはなく、
`ご利用日時` という文字列も存在しない（`◇利用日`）。そのため
「利用通知ではない」と判定され、通知メールが丸ごと対象外に落ちていた。

**教訓: パーサーは必ず、アプリが実際に保存している本文を見てから書く。**
画面からコピーした文面はメールアプリが整形したもので、別物になりうる。
受信箱でメールを開けば保存されている本文がそのまま見えるので、そこを見る。

**⚠️ 三井住友の穴（本文の注意書き）**

> 携帯電話や公共料金などの継続的なご利用、及び ETCやPiTaPa等、
> 一部の電子マネー利用については通知されません

デビュープラスは**サブスク中心 + 電気代（オクトパスエナジー）**という用途（9.7）なので、
**一番取りこぼしたくない固定費がまるごと速報の穴に落ちる。**
ICOCAのクレジットチャージも電子マネー扱いで通知されない可能性が高い。
→ Vpass の CSV 取込は「あると便利」ではなく**必須**（3章を修正済み）。

**ポケットカード（差出人 announce@pinf.pocketcard.co.jp）**

    いつもＺＯＺＯＣＡＲＤ２をご利用いただき、誠にありがとうございます。
    ■ご利用先    ポケットカード加盟店
    ■ご利用日時  2026/09/23 16:51:00
    ■ご利用金額  6,525円

- **店名は出ない。** 本文の注意書きのとおり「ポケットカード加盟店」「JCB加盟店」
  「VISA加盟店」「Mastercard加盟店」「iD加盟店」またはキャッシングの種別しか入らない仕様
- ZOZOカードは用途がZOZOTOWNの衣類のみなので、**口座で費目が決まる**シード済みルール
  （「ZOZOカードの利用はすべて被服費」）で足りる。他の用途のカードだったら成立しない
- 差出人 `announce@` は宣伝メールと共通。**差出人では選り分けられない**ため、
  本文に `■ご利用日時` と `■ご利用金額` があることを利用通知の条件にする

**両社に共通: これは「承認照会」の通知であって確定ではない**

どちらの本文にも「カードのご利用及びご請求を確定するものではありません」とある。
**取消・返品されても訂正メールは来ない。** 与信の仮押さえ額と実際の請求額がずれる
こともある。メール由来の取引は暫定として扱い、CSVを正として上書きする方針で確定。

**⚠️ GASの「送信済みラベル」方式は成立しない（2026-09-23 判明）**

9/23 に利用通知メールが2通届いたのに、アプリには1通も入ってこなかった。
受信箱には 9/22 の4通があるきりだった。

原因は GAS 側の重複防止の作り。送信済みのスレッドに `money-sent` ラベルを付け、
`-label:money-sent` で除外していた。**Gmail のラベルはスレッド単位**であり、
カードの利用通知は**毎回まったく同じ件名**で届くため Gmail が同一スレッドに
まとめる。結果:

    9/22 1通目を送信 → スレッドにラベルが付く
    9/23 新着が同じスレッドに入る → 除外される → 二度と送られない

**最初の1通で蓋がされ、以降が永久に失われる。** 気づきにくく、影響が大きい。

対処: ラベル方式をやめ、**直近7日ぶんを毎回まるごと送る**。サーバーは
`email_messages` の `unique(user_id, gmail_id)` で重複を弾くので、
何度送っても増えない。送りすぎは無害、送り漏らしは致命的なので重い側に倒す。
過去30日を送り直す `backfillCardEmails()` も用意した。

**教訓: 冪等性はサーバー側の一意キーで担保する。** 送信側に「送信済み」の
状態を持たせると、その状態の粒度（ここではスレッド）が送りたい単位
（メッセージ）とずれた瞬間に破綻する。

**⚠️ 三井住友の利用通知は「カードごと」に設定する（2026-09-23 判明）**

デビュープラスには通知が届くのに、Amazonカードには届かなかった。
Vpass のご利用通知サービスは**カード単位の設定**で、1枚ONにしても他のカードは
OFFのまま残る。通知する金額の下限も同様にカードごと。

**カードを追加したら、そのカードの通知設定を必ず確認すること。**
届かないカードがあったときに最初に疑うのはここ。次に疑うのが
「Amazonは発送時に売上が立つ」（注文時点ではまだ通知されない）。

**PayPayカードの用途（2026-09-23 本人談）**

通信費専用ではなく、ときどき普通の支払いにも使っている。
→ ZOZOカードのような「口座で費目を決め打ちする」やり方は**使えない**。
店名ベースのルールが要るので、**PayPayカードの通知メールに店名が入るかどうか**が鍵になる。
入らない場合、このカードはCSV取込が主役になる。

三井住友（デビュープラス）とポケットカード（ZOZOカード）の利用通知が、

画面が一切変わらない。何件をどう処理したかを必ず文言で返すようにした。
iPhone にはカーソルが無いので、押下中の見た目と送信中の表示も全ボタンに入れた。

### メール速報とCSVの重複排除（2026-09-23 実装）

`src/lib/merge-email.ts`。CSV取込のときに、同じ口座の**メール由来の取引**を探して
**上書きする**（新しく足さない）。メール速報は承認照会の通知で確定ではないため、
CSVを正とする。

照合の条件:

| 条件 | 内容 |
|---|---|
| 金額 | 完全一致 |
| 日付 | ±3日。速報は売上データの到着時に配信されるので利用日とずれる |
| 店名 | 正規化して前方一致・部分一致・共通接頭辞4文字以上のいずれか |

**店名が出ないカードは金額と日付だけで照合する。** ポケットカードの利用先は
「ポケットカード加盟店」等しか入らないため、店名として比較しても意味がない。
ただしその場合、**候補が複数あったら自動では決めない**。取り違えて別の買い物に
マージするより、二重に並べて人に気づかせるほうが直しやすい（警告を出す）。

**人が決めた費目は上書きしない。** 未分類トレイで分類済み（confirmed かつ
費目あり）の行は、CSVの分類で塗り替えない。`email_message_id` も残すので、
どのメールから始まった取引かは後からも辿れる。
